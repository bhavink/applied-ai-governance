Unity AI Gateway

Three layers: AI assets in Unity Catalog, AI traffic through a central control plane, and AI service behavior governed by policies.

Spend control, audit trails, and risk reduction. How to implement and where not to put it.

The issue

AI traffic accumulates faster than anyone wires up governance for it.

A typical rollout: a production agent on Databricks Apps, a Genie space, developers using Cursor or another coding agent, a custom MCP server built last quarter, and an external model API a team wired up directly. Each path was built independently, by a different team, at a different time.

AI surfaceWhere its calls are recorded today
Coding agent (per developer)Vendor portal, if the vendor exposes one
Production agent on AppsAgent logs and MLflow traces, if instrumented
Genie spaceIts own dashboard, separate from everything else
Custom MCP serverServer stdout or a bucket somewhere
External model API (direct)Whatever the calling team happened to log

The concrete cost: no single place to see every AI call, guardrails applied on some paths and not others, and no way to answer “what did this cost, and was it safe” without polling every system separately.

What it is

Three architectural layers, one control point.

AI assets: Unity Catalog securables (models, MCP Services, Agent Services, connections). AI traffic: Central control plane for rate limits, fallbacks, spend caps, usage tracking, and inference logging. AI service behavior: Service Policies govern content and tool calls; guardrails are a built-in subset.

Traffic Layer

LLMs & Coding Agents

Agents, LLM endpoints, coding agents (Cursor, Codex CLI, Claude Code), Databricks Apps agents. Native multi-provider: OpenAI, Anthropic, Cohere, Bedrock, Vertex AI, Gemini Enterprise, custom OpenAI-compatible.

Traffic Layer

MCP Services

MCP servers registered as Unity Catalog securables. Tool-level filtering and service policies govern which tools are callable by whom, under what conditions.

Traffic Layer

Agent Services

AI agents registered as UC securables. Governed alongside tables, models, and functions in the same identity model.

Control plane governs: permissions (UC) · rate limits · service policies · spend caps · usage tracking · inference logging · fallback routing.

What it is · Request flow

Two enforcement points: ON CALL and ON RESULT.

Service policies evaluate before invocation (ON CALL) and after response (ON RESULT). Both fail closed — a misconfigured or errored policy blocks the interaction.

Calleragent · coding tool · app
↓
ON CALLAuthentication · Authorization · Rate limits · Input policies
↓
DestinationLLM · MCP service · external API
↓
ON RESULTOutput policies · Usage logging · Inference tables
↓

One request_id joins all events: system.ai_gateway.usage (cost, principal, blocking decisions) and inference tables (payloads, policy evaluations, latency).

What it is · Service policies

Attribute-based access control for AI services.

Service policies govern content and tool calls based on caller identity and request attributes. They run at ON CALL (before invocation) and ON RESULT (after response), and they fail closed — a blocked policy returns HTTP 400, a timeout also blocks.

CategoryScopeExamples
Content guardrailsLLM input/outputPII redaction/blocking, unsafe content, jailbreak detection, hallucination detection, custom (user-defined)
Tool call policiesMCP service invocationBlock a tool, require approval before execution, allow only specific contexts
Caller-based policiesIdentity + contextDifferent rules for different users, groups, service principals; context from caller attributes
Approval workflowsHuman-in-the-loopPause and request human approval before proceeding (content, tool invocation, or both)

Fail-closed by default: A misconfigured service policy, an evaluator timeout, or a policy evaluation error blocks the request. Use mode=LOG to test policies on production traffic without enforcing.

What it is · Guardrails (built-in service policies)

Six guardrail templates, evaluated on every call.

An LLM evaluator (recommended: databricks-gpt-5-nano) scores every request and response. Configure per phase (input/output), per action (block/sanitize), per mode (enforce or log).

TemplatePhaseActionWhat it catches
PII RedactionInput / OutputSanitizeReplaces PII with placeholders (e.g. [EMAIL]) before the model sees it or the user sees the response.
PII BlockingInput / OutputBlockRefuses the request entirely if the payload contains PII — stricter option for regulated workloads.
Unsafe ContentInput / OutputBlockHate speech, harassment, violence, self-harm, sexual content, weapons, extremism.
JailbreakInput onlyBlockInstruction overrides, obfuscated payloads, role-play exploits, prompt extraction attempts.
HallucinationOutput onlyBlockOutput unsupported by retrieved context — useful where grounding matters (RAG).
CustomInput / OutputYou chooseYour own evaluator prompt, up to 5,000 characters — domain-specific policy.

Fail-closed. Blocked request returns HTTP 400. Evaluator timeout or parse error also blocks (use mode=LOG for dry-run). Service policies extend beyond content filtering to govern tool calls and approvals.

What it is · Where the gateway fits

Managed paths vs. passthrough: the critical trade-off.

TrafficRoutingWhat you keepWhat you lose
Agent ↔ Genie, Agent Bricks, Vector Search, custom MCP on AppsDirectPer-user data access control via OBO. Row filters, column masks apply correctly.N/A — internal Databricks traffic.
LLM endpoints, external models (OpenAI, Anthropic, Bedrock, Vertex AI, Gemini)ManagedUsage tracking, rate limits, service policies, model access control, inference tables, cost attribution via request tags.None. This is the right path.
External LLM API with features we don’t yet wrap (e.g. batch endpoints, files API)PassthroughRoute the request unmapped. Selective header/query param forwarding.Usage tracking, rate limits, service policies, model access control, inference tables. Operator beware.
External clients (enterprise apps, partners) calling DatabricksExternal gatewayBoundary crossing from external identity → Databricks token. Then managed paths or direct.None — external gateway is additive.

Critical: Never put the gateway in the OBO path. Internal agent-to-Genie or agent-to-MCP calls must stay direct. The gateway re-issues its own token, so current_user() becomes the gateway’s identity, and row filters silently evaluate wrong.

Why it matters · Cost

Spend caps that block, not just alert.

Hard spend caps

Unity AI Gateway supports spend budgets with shared and per-user thresholds. Thresholds can be configured either to alert or, when block usage is enabled, to stop further requests until the budget resets or an admin raises the threshold. Enforcement is near real time, so a small amount of overspend may still occur.

# budget config shape
budgets:
  - scope: shared | per_user
    period: monthly
    limit_usd: 500
    action: alert | block
$18k → $500
an unbounded batch run capped by a hard budget, illustrative example

Unified spend query

Join system.billing.usage to system.ai_gateway.usage by usage_context tags — the same UC query model finance already uses. No export pipeline.

Why it matters · Risk & compliance

One audit trail answers a question that used to take days.

An agent that calls an LLM, then an MCP tool, then another LLM is three governance domains without a gateway. With one, it is a single trace.

Before

“Show me every AI call this org made last week” means checking a coding-agent vendor portal, agent logs, a Genie dashboard, a custom MCP server’s stdout, and whatever the team using an external API happened to log. Days, not minutes — and still incomplete.

After

One query against system.ai_gateway.usage plus inference tables. Every principal, every endpoint, every guardrail decision, joinable to billing. Minutes, not days.

Fail-closed guardrails mean a blocked request is a recorded decision, not a silent pass-through — the audit trail includes what was stopped, not just what succeeded.

Why it matters · Velocity

Swap models and providers without touching application code.

Fallback and traffic splitting

Primary provider fails → gateway routes to a secondary served entity automatically. A/B test a new model on a percentage of traffic. Stage a rollout from one provider to another with built-in comparison metrics — no client code changes.

Coding agents and Apps agents inherit the same controls

Cursor, Codex CLI, Gemini CLI, and Claude Code point at OpenAI-compatible base URLs. A Databricks Apps agent changes one base URL. Both inherit permissions, rate limits, guardrails, usage tracking, and cost attribution — with zero additional wiring.

Native provider APIs, not a translation layer. Each provider’s SDK works unchanged against the gateway’s native surface — streaming, system prompts, structured tool use all behave exactly as the SDK expects.

How · Getting it running

Four steps to a governed endpoint.

1
Enable

Account admin enables Unity AI Gateway from the account console (workspace-wide flip).

2
Create model service

Pick a target model (FMAPI, external provider, custom). Attach rate limits, guardrails, and service policies.

3
Grant permissions

Add users, groups, and service principals to UC securable EXECUTE grants — same identity model as UC tables.

4
Point clients

Update agents, coding tools, and apps to the gateway base URL. Existing SDKs work unchanged.

Native provider APIs
from openai import OpenAI
client = OpenAI(
  base_url="https://<uag>/v1",
  api_key=DATABRICKS_TOKEN,
)
response = client.chat.completions.create(...)
from anthropic import Anthropic
client = Anthropic(
  base_url="https://<uag>/anthropic/v1",
  api_key=DATABRICKS_TOKEN,
)
response = client.messages.create(...)

Same for Gemini, Cohere, custom OpenAI-compatible. Coding agents use /cursor/v1, /codex/v1.

How · Existing serving endpoints

Already in production? Layer the gateway on with one API call.

PUT /api/2.0/serving-endpoints/<name>/ai-gateway

  "guardrails": {

    "output": {"safety": true, "pii": {"behavior": "BLOCK"}}

When to use the layered path

  • Existing serving endpoints in production — flip on gateway features without re-pointing clients
  • Guardrail needs are covered by safety / PII / keyword filters, not the full six-template catalog
  • You want classic inference-table audit on a custom model endpoint
  • Workload isn’t on the coding-agent / native-API path yet — both paths coexist
How · Configuring runtime controls

Rate limits, spend caps, and service policies — three separate levers.

LeverGovernsDetail
Rate limitsCall volumeQPM (calls) and TPM (tokens), per endpoint/user/group/SP. Precedence: endpoint ceiling > named SP override > user default > group default. Max 20 limits per endpoint. Updates propagate in ~60s.
Spend capsDollar budgetHard block at threshold, per endpoint/user/account. Enforced on near-real-time cost estimate (can overspend slightly). Returns 429 when exhausted. Pair with rate limits for multi-layer cost control.
Service policiesContent + tools + approvalABAC: enforce rules before invocation (ON CALL) and after response (ON RESULT). Allow, deny, or require human approval. Block tool invocation by principal or context. Fail closed.

Managed vs. passthrough trade-off: Managed paths give you all controls (rate limits, spend caps, service policies, inference tables, model access control). Passthrough bypasses governance for provider features not yet wrapped. Default to managed paths.

Things to know

What breaks quietly if you skip the fine print.

IssueDetail
Gateway in OBO pathCritical: never put the gateway in the OBO path between an agent and Genie, Agent Bricks, or a custom MCP server. The gateway re-issues its own token, so current_user() becomes the gateway’s identity, and row filters evaluate silently wrong. Keep internal Databricks-to-Databricks traffic direct.
Guardrails don’t soft-failGuardrails fail closed. An evaluator timeout, parse error, or misconfiguration blocks the request (HTTP 400). Use mode=LOG for dry-run testing without enforcement.
Spend cap is a hard blockNot a soft alert. Requests return 429 once the budget is hit. No manual override until the billing period resets or an admin raises the cap.
Output guardrails + streamingOutput guardrails evaluate post-response, so streaming responses bypass them. Use input guardrails or non-streaming requests for output policy enforcement.
Passthrough loses governancePassthrough paths (provider features not yet wrapped) bypass rate limits, service policies, and inference tables. Operator beware.
Production checklist

Before this goes live.

UC permissions: least privilege

Grant EXECUTE to specific groups, not workspace-wide. Coding agents accessible only to developer groups.

Rate limits per principal

QPM and TPM caps; tighter limits for service principals than human users. Endpoint ceiling > individual overrides.

Service policies in LOG mode first

Test guardrails on production traffic in mode=LOG dry-run before switching to mode=ENFORCE.

Spend caps + rate limits together

Rate limits control traffic volume. Spend caps control dollars. Use both as multi-layer cost control.

Inference tables configured

UC catalog with retention policy, audit-grade access controls. Join to system.billing.usage for cost analysis.

Internal Databricks traffic stays direct

Confirm no gateway sits between agent and Genie, Agent Bricks, or custom MCP server. OBO path must be direct.
