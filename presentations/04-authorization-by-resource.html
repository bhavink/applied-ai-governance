Authorization by Resource Type

What access control looks like at each Databricks AI resource — the identity model, OAuth scopes, the gotcha for each, and the pattern that works.

Companion to token fundamentals. That covers how you get the token; this covers what each resource enforces once it arrives.

Agenda

Seven resources. Seven different authorization models.

1. OAuth scopes — what they control, the endpoint vs scope confusion, M2M vs OBO tokens

2. Serving endpoints, Genie, Vector Search — identity model for each

3. UC Functions and HTTP Connections — safe boundaries for writes and external systems

4. Tables — row filters, column masks, current_user() vs is_member()

5. Lakebase — PostgreSQL-native grants and RLS, not Unity Catalog

6. Decision guide and production-readiness checklist

The problem

Authorization is enforced at the resource, not by the app.

The same token can be valid for Model Serving but rejected by Genie. Vector Search sees one user, Lakebase sees another. Row filters in UC work one way in notebooks and a different way in Agent Bricks. Getting the token right is table stakes, but it's only the first check.

What — Serving Endpoints & Agent Bricks

OBO extracts the user, but only inside the serving endpoint itself.

Identity model

  • OBO: Pass user's OAuth token in Authorization: Bearer {token} header
  • Inside endpoint: ModelServingUserCredentials() extracts user identity
  • Scope: model-serving
  • M2M: App SP credentials auto-injected by platform

The ModelServingUserCredentials trap

ModelServingUserCredentials() only works in Model Serving context. In Databricks Apps, it silently falls back to SP credentials — wrong identity, no error.

Fix: In apps, read X-Forwarded-Access-Token and pass explicitly to the endpoint.

What — Genie Spaces

OBO only. Both scopes required. is_member() breaks silently.

Identity model

  • OBO only — user's token via Authorization: Bearer {user_token}
  • Both genie AND dashboards.genie scopes required (UI doesn't show both)
  • current_user() = caller human email
  • is_member() = Genie execution service (not the caller)

The scope trap

App integration UI lists only dashboards.genie. Genie API checks for both. Missing genie scope = 403 with cryptic error.

Fix: Add both scopes via account API or CLI, not the UI.

What — Vector Search

M2M only. Same results for all users. Filtering is application-layer.

Identity model

  • M2M only — App SP has CAN_SELECT on the index
  • WorkspaceClient() auto-discovers SP credentials
  • Scope: vector-search
  • current_user() = App SP UUID (not per-user)

No native per-user identity. Vector Search returns the same top-K to all users. Per-user access is your responsibility.

Filtering options

Pre-filterInclude user/group metadata in index, filter in query. Fast but requires data enrichment.
Post-filterApp retrieves results, checks each against user ACL. Flexible, uses retrieval budget.
Shared KBM2M as-is: everyone sees same docs, no filtering needed.
What — UC Functions

The authorization boundary for writes: EXECUTE on the function, not the table.

CREATE FUNCTION prod.auth.approve(
  deal_id STRING
)
RETURNS STRING LANGUAGE SQL
RETURN (
  UPDATE prod.sales.deals
  SET status = 'approved'
  WHERE id = deal_id
    AND current_user() IN (
      SELECT email FROM
      prod.sales.approvers
    )
);

Pattern

Agent SPHas EXECUTE on function only
Agent SPNO UPDATE/INSERT on table
FunctionChecks current_user() internally
Audit logFunction calls appear in system.access.audit

Function is the authorization boundary. Agent never has direct write access.

What — UC HTTP Connections

Five auth methods. Only two pass per-user identity to the external service.

MethodExternal seesUse case
Bearer TokenShared static tokenSimple integrations, static API keys
OAuth M2MShared app credentialsService-to-service at org level
OAuth U2M SharedOne admin's delegated tokenShared admin access
U2M Per UserUser's own identity ✓As the user (Jira, GitHub, etc.)
Managed OAuthUser's own identity ✓Google, Microsoft Graph — Databricks handles OAuth flow

Kill switch. REVOKE USE CONNECTION immediately blocks agent access — no redeploy needed.

No granular scopes. UC controls WHO can use connection. For different operations (read vs write), create separate connections with different credentials.

What — Tables

Row filters and column masks work everywhere, but is_member() has a gotcha in OBO.

Row filters & column masks

  • SQL function evaluated at query time, attached to the table
  • Fires in all access paths: notebooks, apps, Genie, agents, API
  • Column masks transform values per user — same trigger rules as row filters

current_user() vs is_member()

Access pathcurrent_user()is_member()
NotebookHuman ✓Human groups ✓
App SQL (OBO)Human ✓Human groups ✓
Genie (OBO)Human ✓Genie service ✗

Rule: Use current_user() everywhere. It works in all paths. is_member() breaks silently in Genie and Agent Bricks OBO — no error, just wrong rows.

What — Lakebase

PostgreSQL-native authorization. Not governed by Unity Catalog.

Lakebase identity model

  • Scope: postgres (for management API only)
  • Auth: Databricks OAuth token as PG password OR native PG role
  • App's SP client ID = PG role name (auto-created on binding)
  • Access: GRANT on schema/table + PostgreSQL RLS policies
NOT Unity Catalog

Two access paths, different auth

Direct PG connection: PG roles + GRANT + RLS enforce access.

Via lakehouse API: Unity Catalog policies apply.

Same table. Different authorization model per access path.

Why it matters

Authorization failures return wrong data, not errors.

Security

A row filter using is_member() in Genie leaks data silently — no error, just wrong rows to the wrong user.

Compliance

Lakebase data behind both UC and PG policies. Auditors need to know which layer enforced which control. You need to know too.

Scaling

UC Function as authorization boundary means every new agent gets the same safety boundary without re-derivation.

Authorization lives at the resource. The right token path is only the first check. Know which resource enforces which control.

How — Decision guide

Three questions that determine the authorization pattern.

Question 1

Which resource?

Serving Endpoints, Genie, Vector Search, Functions, HTTP Connections, Tables — UC + scopes.

Lakebase — PG GRANT + RLS, not UC.

Question 2

Per-user identity needed externally?

Yes — U2M Per User or Managed OAuth connection.

No — Bearer token or M2M OAuth.

Question 3

Agent needs to write?

Yes — UC Function with EXECUTE grant (boundary for writes).

No — Row filters and column masks on the table.
