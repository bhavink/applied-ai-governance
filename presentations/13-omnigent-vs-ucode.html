Coding Agents on Databricks01 / 16
Why this deck exists

Three tools, one job, easily conflated.

They all route a coding agent through a governed model endpoint. That is where the similarity ends. Two are the same engine at different hosting levels; the third is a different category entirely.

Same engine

Omnigent OSS

  • Apache 2.0 meta-harness you host
  • Full policy engine + sandbox
  • Bring any model credentials
Same engine, hosted

Omnigent managed

  • Databricks runs the server
  • Built-in policies, workspace auth
  • Zero setup
Different category

ucode

  • Thin CLI launcher
  • Auth + routing only
  • No sessions, sandbox, or policy

Open source vs managed is a hosting choice, not a feature paywall. ucode is not a "lite Omnigent."

The landscape02 / 16
Shared vocabulary

These seven words get conflated.

Client

Terminal, browser, app, or phone that submits turns. It renders output; it does not run the agent.

Agent

A declarative spec (a YAML recipe): which harness, model, sandbox, policies, and prompt.

Harness

The runtime that executes an agent's turns. Wraps one coding-agent CLI behind a uniform contract. Swap in one line.

Host

The machine the agent loop runs on. Either the serverless compute plane or your own registered laptop.

Sandbox

The jail the agent runs inside, on whichever host. Omnibox: bubblewrap plus seccomp on Linux, Seatbelt on macOS.

Policy

A rule on the agent's actions. ALLOW, ASK (pause for approval), DENY, plus TRANSFORM to rewrite. Stateful across a session.

Skill

A named bundle of instructions and files the model loads on demand. Distinct from a tool (a callable with a schema).

Host and Sandbox cause the most trouble. A host is where; a sandbox is how tightly. Next slide pulls them apart.

Key terms03 / 16
Host vs sandbox

Three nested things, often heard as one.

The server decides. The host executes. The sandbox confines. In managed mode Databricks always runs the server, but the host underneath is a choice you make per session.

Server · control plane

Sessions, auth, policy evaluation, inference routing, durable transcript. Managed: Databricks runs it. OSS: a local subprocess on 127.0.0.1:6767.

Host · execution plane

Where the agent loop, the working tree, and tool execution actually live. Dials the server outbound over wss; the server never dials in.

Sandbox · confinement

Omnibox wraps the harness on whichever host: read-only system binds, dotfiles masked, default-deny egress proxy, seccomp denylist on Linux.

One server, many hosts, one sandbox per session. Swapping the host does not change the governance surface; it changes where your source code sits.

Omnigent sits in the agent loop.

The meta-harness05 / 16
Install · setup · run

What each command actually does.

install
uv tool install fetches the wheel from PyPI. Writes shims + PATH. No server contacted.
setup
Local reads of env keys + profiles. Secrets to OS keychain. No token minted here.
run
Spawns a local server on 127.0.0.1:6767 + a runner. Runner dials the server; server dials the model.
persist
Session + history to ~/.omnigent/chat.db (SQLite) or Postgres/Lakebase; artifacts to disk / S3 / UC Volumes.

All local and outbound-only. The credential lands in your keychain; the workspace token is minted lazily at first turn.

Managed topology07 / 16
Managed, two ways

Managed picks the server for you. You still pick the host.

Host A · serverless compute plane

Databricks runs the machine

› Source code is cloned into the serverless host, not your laptop
› Omnibox always on; Linux bubblewrap plus seccomp, the hard-isolating backend
› Inference forced through AI Gateway. No bring-your-own model key
› Credential never lands in the sandbox; a placeholder is swapped at approved egress
› Nothing to install and nothing left running on your side
Host B · your registered machine

You run the machine, Databricks governs it

› Source code, working tree, and tool execution never leave your disk
› Omnibox available, but weaker on macOS (no syscall filter) and disable-able
› AI Gateway is the default route, not a hard requirement
› Model credential stays in your keychain, used directly by the harness
› Your existing local toolchain, mounts, and network access carry over

Same server, same policy engine, same sessions. The host choice trades code locality against isolation strength. Pick B when source cannot leave the machine; pick A when you want the strongest sandbox on any laptop.

One turn, two deployments

The same prompt, traced end to end.

OSS · self-hosted

Everything on your machine

Managed

Control leaves, code may not

01You open <workspace>/omnigent and log in with workspace OAuth
02Databricks already runs the server. Nothing to start

Steps 04 through 06 are identical in shape. What moves is who owns the server, who owns the transcript, and whether inference is forced through the Gateway.

Interaction trace10 / 16
Defense in depth

Two independent guardrail layers.

Layer 1 watches what the agent does. Layer 2 watches what the model sees and says. Different questions, different enforcement points, neither substitutes for the other.

Layer 1 · in the agent loop

Omnigent policies

› Six hook phases: REQUEST, TOOL_CALL, TOOL_RESULT, RESPONSE, LLM_REQUEST, LLM_RESPONSE
› Four verdicts: ALLOW, ASK, DENY, plus TRANSFORM to rewrite the action
› Stateful: a handler takes (old state, new event) and returns (verdict, new state) for the whole session
› Named policies: intent-based authorization, risk score, cost budget, no-write-down on documents
› Fail-closed on TOOL_CALL and REQUEST. DENY short-circuits; ASK accumulates
› Runs even under CLI bypass mode, so it is not opt-out
Layer 2 · at the inference endpoint

Unity AI Gateway

› Content guardrails on prompt and completion: safety, PII, keyword blocklists, jailbreak
› Rate limits by queries and tokens per minute, per user and per endpoint
› Budgets per user and workspace, enforced before the call reaches a model
› Usage and spend recorded in system.ai_gateway.usage under workspace identity
› Fallback routing across providers when one endpoint degrades
› Applies to every caller of the endpoint, agents and apps alike

Omnigent alone gives layer 1. ucode alone gives layer 2. Managed Omnigent through the Gateway is the only combination with both.

Worked example12 / 16
Omnibox sandbox

Kernel-level isolation, credentials never exposed.

FS
Read-only system binds; individual /etc files only; dotfiles masked
Net
Default-deny egress proxy; blocks private IPs and metadata endpoints
Syscall
seccomp denylist on Linux; mount, ptrace, module load blocked
Creds
Agent holds a placeholder; real secret swapped in only at approved egress

A leaked placeholder is worthless: it is bound to one host, needs a per-session token to reach the proxy, and is never attached to reflection methods. Network and credential protections require a hard-isolating backend, which today means Linux. On macOS, Seatbelt grants capabilities but adds no syscall filter; on Windows, job objects contain the process without isolating filesystem or network. This is the strongest argument for a serverless host.

Matrix14 / 16
Choosing

Pick by constraint, not by brand.

Just per-user auth + usage on an installed agent?→ ucode
Shared sessions, sandbox, spend + approval gates?→ Omnigent managed
Source code cannot leave your machine?→ managed + local host
Want the strongest sandbox, on any laptop OS?→ managed + serverless host
Custom policies, own host, or your own model keys?→ Omnigent OSS
A UI-driven data app, not a coding agent?→ Agent Bricks / Genie

Each option is the right answer for its constraint. They compose: start with ucode, graduate to Omnigent when you need sessions and governance.
