Managed Omnigent Security01 / 19
First, a correction

"Managed" is a per-session setting, not a product tier.

A session created with host_type="managed" makes the server provision a cloud sandbox, start a host inside it, and wait for it to register. From there it uses the identical machinery an external host uses.

Server

Always Databricks

  • Sessions, auth, permissions
  • Policy evaluation
  • Durable transcript
Host · the variable

Sandbox or your laptop

  • Runs the agent loop
  • Owns the working tree
  • Chosen per session
Sandbox

Confines the harness

  • Omnibox on either host
  • Strength varies by OS

One server can run managed-sandbox sessions and laptop-host sessions side by side. So "is my code on Databricks infrastructure?" is answered per session, not once by a contract. server/managed_hosts.py:1-9

Terminology02 / 19
The question everyone asks first

Does Databricks open a connection into my network?

No. Every hop dials outward.
Host → Server OUTBOUND The host is a WebSocket client. It binds no listening socket at all. host/connect.py:714, 930-939
Runner → Server OUTBOUND Same pattern. The code says it plainly: "The runner is the WebSocket client." runner/transports/ws_tunnel/serve.py:262-268
Server → Host NEVER DIALS Control rides down the tunnel you opened, as a host.launch_runner frame. server/managed_hosts.py:6-9

This is why the design suits egress-only firewalls and Private Link. Tunnel reconnect: 0.5s initial, 10s cap, ±50% jitter. host/connect.py:292-294

Inbound03 / 19
Being precise

The harness does listen. On a socket only its parent can reach.

A security review deserves the caveat rather than a flat "nothing listens." The harness binds a local endpoint the parent allocated. It is never on a network interface.

POSIX · macOS and Linux

Unix domain socket

› Path under /tmp/omnigent-{uid}/
› Directory mode 0700, socket mode 0600
› Owner-only; unreachable over any network

Windows

Loopback TCP

› Binds 127.0.0.1 only
› Ephemeral port allocated by the OS
› Enforced: exactly one of socket or bind is required

Listening sockets04 / 19
Where things run

Four processes. Your code runs in the last one.

server
Sends host.launch_runner down the tunnel the host already opened. Never executes agent code.
host
Spawns the runner as a subprocess with RUNNER_SERVER_URL and a binding token. host/connect.py:591-592
runner
One per session. Resolves harness type and spawn env from the agent spec. runner/app.py:2385-2410
harness
Your code and its tools execute here, inside Omnibox, on the host. runner/app.py:1-10

In a managed session all four sit on Databricks infrastructure. In an external-host session, host, runner, and harness are on your machine and only the server is remote.

Process chain05 / 19
Inference egress

Model calls leave the harness directly.

Credentials are injected into the harness at spawn from a fixed allowlist, and the harness calls the base URL it was handed. The Omnigent server does not proxy, cache, or inspect model traffic.

Governance consequence, stated bluntly. Because inference leaves the harness directly, routing it through Unity AI Gateway is a configuration property — the base URL the harness was given — not a structural guarantee of the topology. If your guardrail and usage-tracking story depends on Gateway transit, verify it with traffic, per session type.

Tenancy07 / 19
The one finding to act on

Isolation holds only if a permission store is wired.

The access check opens with an early return. A None store turns every session permission check into a no-op — a silent allow-all across all users.

async def _require_access(user_id, conversation_id, required_level,
                     permission_store, conversation_store):

    if permission_store is None:
        return  # every check below is skipped

server/routes/_auth_helpers.py:120-121

This is a sane default for a single-user laptop and a catastrophic one for a shared deployment. It is not a defect to report upstream — it is the top verification item. Prove it with traffic: authenticate as user B, request user A's session id, require a 404. A configuration read will not reveal this.

UI hosting09 / 19
Data at rest

The application encrypts nothing. That is the platform's job.

Verified by absence as much as presence: no SQLCipher, pysqlcipher, pgcrypto, or envelope encryption anywhere in the package, and engines are built with plain SQLAlchemy and no cipher parameters.

Conversation content — conversation_items.data, plaintext JSON in a Text columnplaintext
Search index — search_text, an extracted plaintext copyplaintext
Comments — CompressedText, zstd level 19. Compression is unkeyed and reversiblenot encryption
Host launch tokens — SHA-256 digest only, raw token never storedhashed
Device codes and refresh tokens — HMAC-SHA256, plus prev-hash for replay detectionhashed
Lakebase connection — OAuth token minted per connection, ~1h life, 10min pool recycleshort-lived

So at-rest protection is entirely Lakebase and UC Volumes. Reasonable architecture; attribute the control correctly. Whether a workspace uses CMEK is not in the code — ask, because "encrypted at rest" and "encrypted with your key" are different answers. db/db_models.py:904 · db/utils.py:198-254

Encryption10 / 19
Managed sandbox

Inbound: none. Outbound: default-deny.

Outbound

Allowlist proxy with metadata traps

› L7 proxy matches every request against an allowlist; empty list denies all
› Blocked: RFC1918, CGNAT, loopback, link-local, reserved, multicast
› Cloud metadata trapped: AWS 169.254.169.254, Azure 168.63.129.16, Alibaba
› Relay port chosen by the parent so nothing can pre-squat it

inner/egress/proxy.py:140-184 · sandbox.py:113-116

Inbound

No path in

› Only endpoint is the 0600 UDS or loopback TCP
› Reachable solely by the parent runner at the same UID
› $HOME is never mounted
› Dotfiles masked: .aws .ssh .gnupg .kube .netrc .databrickscfg

bwrap_sandbox.py:30-31, 1096-1151 · seatbelt_sandbox.py:179-198

Credentials never enter the sandbox. Default is swap-on-access: the harness sends no Authorization header and the proxy injects the real secret on the way out. The proxy config is deliberately excluded from the serialized sandbox policy. inner/credential_proxy.py:12-16 · sandbox.py:159-165

Session · memory · skills

What persists, and what quietly does not.

Persists

Session and transcript

› Messages, tool calls, reasoning in conversation_items
› Managed: Lakebase. Self-hosted default: ~/.omnigent/chat.db
› Artifacts to UC Volumes, S3, or local disk
› Skills are files on the host, per-user or per-project
Does not persist

Memory

› A plain Python dict in the process
› Lost on restart. Nothing durable to encrypt or retain
› Scope labels: per_session, per_user, cross_user
› cross_user carries no enforcement — a label on a dict, not a boundary

inner/datamodel.py:199-252

Two things not to overstate: a skill bundled into an agent is readable by anyone who can load that bundle, and there is no skill-level access control. spec/skill_sources.py:93-98

Summary16 / 19
Before you deploy

Seven things a code read cannot settle.

Prove isolation with traffic: user B requests user A's session id→ require 404
Name the sandbox provider backing your workspace→ where code lives
Get the at-rest answer in writing, CMEK or not→ not in code
Set sharing mode deliberately; the default is ON→ restricted
Verify Gateway transit behaviorally, not architecturally→ send traffic
Prefer a Linux managed host for isolation strength→ seccomp
Treat sandbox type none as a review trigger→ audit specs

These are not product gaps. They are the boundary between what the shipped code proves and what the deployment decides, and every one of them is a builder action.
